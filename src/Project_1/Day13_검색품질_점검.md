# Day 13 검색 품질 점검

## 범위와 방법

- 기존 SIF 24건, KOSHA GUIDE 813개 청크, 같은 PostgreSQL/PGVector와 임베딩 모델을 사용했다. PDF·CSV·DB 원본은 변경하지 않았다.
- 대표 질문 10개에 대해 개선 전 원문 질문 벡터 검색과 개선 후 역할별 질문 벡터 검색을 비교했다. 질문 임베딩 요청에는 질문에서 만든 문장만 포함했다. 문서 본문·사고사례·GUIDE 텍스트를 외부 모델에 보내는 SIF LLM 재정렬 및 최종 답변 생성은 실행하지 않았다.
- 표의 SIF는 **LLM 재정렬 전 후보 상위 3건**, KOSHA는 **로컬 섹션/메타데이터 재정렬 후 상위 3건**이다. 따라서 표의 SIF 후보 순위를 실제 화면의 최종 SIF 순위로 해석하면 안 된다.

## 적용한 변경과 이유

1. `equipment / work_type / hazard / intent`를 구조화한 **Work Context**를 만들었다. 후속 질문에서는 이전 대화가 장비/작업을 보충하지만, `예방`, `점검` 같은 현재 발화의 의도를 우선한다.
2. SIF에는 **유사 사고·사고 원인·재해유발요인** 중심 질의를, KOSHA에는 **점검·작업방법·안전조치** 중심 질의를 각각 보낸다. SIF 기인물/재해유발요인 조건은 해당 사례가 1~2건만 있어도 우선 후보에 넣고 전체 검색으로 후보 10건을 보충한다.
3. KOSHA는 수집된 GUIDE 범주로 좁히고, `목적/정의/부록`과 서식 예시·개요 본문을 낮추며 `안전/점검/금지/작업방법` 섹션을 높인다. 장비·작업·위험 metadata, 질문 의도와 점검 시점도 점수에 반영한다. 사다리 `A-G-4-2025`는 Day 9 OCR이 뒤쪽 페이지를 `정의`로 잘못 표시했으므로 조회 시 페이지만 보고 섹션명을 보정한다.
4. 최종 Prompt에서 **SIF=실제 사고·원인**, **KOSHA=공식 기술지침의 점검·조치** 역할을 분리했다. 근거가 부족하면 한계를 밝히고 임의 사고 경위나 점검 항목을 보태지 않도록 지시했다.
5. Streamlit의 접힌 **개발용 검색 진단**에서 해석된 Query, SIF/KOSHA 상위 결과, 거리·재정렬 점수·이유를 볼 수 있다. 기본 화면에는 원시 Document가 나오지 않는다. 기존 `chat_history` 저장/조회 코드는 변경하지 않았다.

## 검증과 남은 실패 유형

- 10개 질문의 로컬 검색 비교 완료. Streamlit 초기 화면은 예외 없이 열렸고 상담 탭·통계 탭·채팅 입력이 표시됐다. 합성 분석 결과를 넣은 채팅 UI 점검에서도 사용자/AI 메시지와 접힌 개발용 검색 진단이 오류 없이 표시됐다. Work Context 5종, 후속 질문 의도, 프롬프트 변수 및 Python 문법 점검을 통과했다.
- **최종 답변의 실제 문장과 SIF LLM 재정렬 Top 3는 전후 비교하지 못했다.** 검색 문서 본문을 외부 LLM으로 보내는 평가 실행이 자동 승인 검토에서 거부되었다. 따라서 위 표의 마지막 열은 검색 근거상 기대되는 변화이며, 생성 답변의 검증 결과가 아니다.
- SIF 사고사례는 24건뿐이라 고소작업대·비계·사다리의 정확한 작업/장비 사례가 부족할 수 있다. 컨베이어는 해당 KOSHA GUIDE가 수집되지 않아 안전기준 부분이 비어 있다. A-G-4 사다리 원문에는 OCR 잡음이 남아 있고, 페이지 기반 섹션 보정은 해당 GUIDE에만 적용된다. 규칙 기반 Query Analyzer는 새로운 장비 표현을 놓칠 수 있다.
