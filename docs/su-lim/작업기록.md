## M1. 데이터 수집·구조 확인 (10/02)

- **한 일**: 원본 6개를 불러와 구조·결측·중복·기준연도를 확인했다.
- **방법**: pandas로 읽고 `head / shape / columns / info`, 결측·중복 요약표를 만들었다.
- **결과**: 1번 엑셀이 RAG용 사고사례 **6,032건**(제조업등 2,573 + 건설업 3,459)이다. 6번은 데이터가 아니라 출처 목록이다.
- **한계**: 원본 사용 조건(재배포·변경 금지 여부)은 팀에서 재확인 중이다.
- **파일**: `notebooks/su-lim/01_data_check.ipynb`, `02_m2_raw_점검.ipynb`

## M2. 전처리 (10/02)

- **한 일**: 결측·이상치·중복 처리 기준을 정하고 표준 용어로 통일해 저장했다.
- **방법**: 결측은 NaN으로 유지했다. ⑤번 결측 14개는 전부 ④번 사업장수가 0인 칸(해당 규모에 사업장이 없음)이라 값이 없는 것이 맞다. 이상치·중복은 삭제하지 않고 기록만 했다.
- **결과**: 정리된 데이터를 `data/processed`에 저장했고 전처리 이유와 기준을 명세서에 적었다.
- **한계**: 삭제하지 않은 중복·이상치는 분석 단계에서 해석에 유의해야 한다.
- **파일**: `docs/su-lim/M2_전처리_명세서.md`

## M3. 기술통계·분석 (10/02)

- **한 일**: 업종별 기인물 분포를 분석하고 핵심 인사이트를 정리했다.
- **방법**: 기술통계 요약, 연도별 사례 수, 기인물 상위, 규모별 사업장당 재해자를 계산했다.
- **결과**: 제조업은 지게차·크레인·컨베이어, 건설업은 비계·고소작업대·지붕 채광판·사다리 등 고소작업 기인물이 상위다. 건설업은 소수 기인물에 집중(상위 8개 36.6%)하고 제조업은 분산(28.3%)한다.
- **한계**: 제조업 기인물 `분류 불가` 398건(15.5%)은 분석에서 결측으로 처리했다.
- **파일**: `notebooks/su-lim/03_m3_기술통계분석.ipynb`, `data/analysis/m3_*.csv`

## M4. 벡터DB 적재 (10/02)

- **한 일**: 사고사례를 임베딩해 ChromaDB에 적재하고 검색을 확인했다.
- **방법**: 사례 1건 = 문서 1개(평균 372자라 쪼개지 않음). 문서에는 업종 분류, 고위험작업·재해종류, 재해개요, 기인물, 재해유발요인, 예방대책을 넣었다. `text-embedding-3-small`로 임베딩하고 코사인 유사도 컬렉션 `sif`(`data/chroma`)에 6,032건을 모두 넣었다. 메타데이터는 업종구분·중분류·기인물·재해종류·재해연도이다.
- **결과**: "지게차 협착" 질문에 지게차 사례 3건이 나왔고, 업종구분=건설업 필터를 건 "비계 추락" 질문에 건설업 비계 사례 3건이 나왔다.
- **한계**: 통계 표는 이 단계에서 넣지 않았다. M7에서 보완했다.
- **파일**: `notebooks/su-lim/04_m4_벡터DB적재.ipynb`

## M5. RAG 체인 (10/02)

- **한 일**: 질문 → 검색 → 답변 → 출처 표시까지 한 흐름으로 만들었다.
- **방법**: 질문을 임베딩해 유사 사례 3건을 찾고, 유사도 `MIN_SIM` 0.40 미만 사례는 버린다. 남은 사례만 근거로 `gpt-4o-mini`가 답하고 `[사례N]`으로 출처를 단다. 근거가 없으면 GPT를 부르지 않고 "제공된 사례에서 근거를 찾을 수 없습니다."로 응답한다.
- **결과**: 범위 안 질문의 최고 유사도 최저값은 0.438, 범위 밖 질문의 최고값은 0.353이어서 그 사이인 0.40을 기준으로 잡았다. 범위 밖 질문 3개(날씨·달 탐사선·파스타)는 모두 근거 없음으로 처리되었다. 범위 안 질문(컨베이어 끼임, 천장크레인, 이동식 사다리 등)은 원인과 예방대책이 출처와 함께 나왔다.
- **한계**: "지붕 채광판"처럼 구체 용어가 "작업 중 추락" 같은 일반 표현에 묻히면 엉뚱한 사례가 검색된다. 후속 개선 과제이다.
- **파일**: `notebooks/su-lim/05_m5_RAG체인.ipynb`

## M6. 골든 셋 평가 (10/03)

- **한 일**: 정답이 있는 질문 100개로 검색이 정답 사례를 얼마나 찾는지 측정하고 실패 원인을 분석했다.
- **방법**: 골든 셋은 사례 84문항 + 통계 16문항이다. 지표는 Hit@1·3·5, MRR@5, Precision@3·5이다. 정답 ID가 DB에 있는지, 정답 확인 문구가 그 문서에 들어 있는지 코드로 검증했다(사례 82/84 일치). 질문을 GPT로 현장 말투로 바꿔 한 번 더 측정했다.
- **결과**:
  - 원본 질문의 사례 Hit@5는 약 0.84(ChromaDB 근사 검색 기준)이다. 전수 코사인(정확 검색)으로 재면 0.869이다.
  - 원본 질문이 사례 본문을 그대로 옮긴 문장이 많아서 점수가 부풀려진다. 현장 말투로 바꾸면 Hit@5가 0.26이다.
  - 통계 16문항은 인덱스에 통계 문서가 없어서 0.00이다. 모델 문제가 아니라 구조 문제이다.
- **한계**: 현장 말투 점수는 정답 1건만 인정해서 낮게 나오는 면이 있다. 그래서 같은 기인물 사례가 상위에 있는지도 함께 본다(참고 지표).
- **파일**: `notebooks/su-lim/06_m6_평가.ipynb`, `docs/su-lim/golden_set_100.csv`, `data/analysis/m6_*.csv`

## M7. 개선 실험 (10/03)

- **한 일**: M6에서 가장 큰 약점인 통계 질문(0.00)을 고치고, 개선 전·후를 같은 100문항으로 비교했다.
- **방법**:
  1. 통계 표(규모별 사고사망자수)를 문서로 바꿔 넣은 `sif_v2`를 만들었다(10개 문서, 한 문서에 22개 연도).
  2. v2는 문서끼리 임베딩이 거의 같아 순위가 불안정했다(유사도 차이 약 0.03).
  3. 그래서 규모×연도 단위로 쪼갠 `sif_v3`를 만들었다(220개 문서, 한 문서에 숫자 하나, ID `통계-<규모>-<연도>`).
  4. 기존 `sif`를 복사해 새 컬렉션을 만들어서 개선 전 상태를 보존했다.
  5. 부작용(사례 검색 점수 하락, 사례 질문 상위 5개에 통계 문서가 섞이는지)과 통계 답변 정확도, MIN_SIM 통과 여부도 확인했다.
- **결과**:
  - v2의 통계 Hit@5는 정확 검색으로 재면 0.875이다. ChromaDB 근사 검색에서는 순위가 흔들렸다.
  - 사례 Hit@5가 0.845에서 0.821로 내려간 것은 통계 문서가 섞인 영향이 아니다. 통계 문서가 사례 상위 5개에 섞인 건수는 0/84이고, 정확 검색으로 확인한 두 문항(Q15, Q72)은 순위가 그대로였다. 새 컬렉션을 만들 때 생기는 근사 검색 오차이다.
  - v3의 통계 정답은 규모와 연도가 모두 맞아야 인정한다(더 엄격한 기준). v3 결과: ○ (07 노트북 9절 참고)
- **한계**:
  - 통계가 규모별 사망자수 한 가지뿐이다. 업종별·재해유형별 통계 질문은 답하지 못한다.
  - 현장 말투 사례 검색(Hit@5 0.26)은 그대로이다.
  - 다음 개선 후보는 질문 앞의 공통 문구를 제거하는 것과 기인물을 메타데이터 필터로 쓰는 것이다.
- **파일**: `notebooks/su-lim/07_m7_개선실험.ipynb`, `data/analysis/m7_*.csv`

## M8. Streamlit 앱 (10/04)

- **한 일**: 사이드바 필터가 두 탭에 공통 적용되는 대시보드와 RAG 챗봇을 하나의 앱으로 만들고 전체 흐름을 실행해 확인했다.
- **방법**:
  1. 화면 설계: 사이드바(업종, 재해 연도, 근거 사례 수 k) + 탭 2개(대시보드 / 챗봇).
  2. 대시보드: M2 전처리 데이터와 M3 분석 결과를 읽어 핵심 지표 4개와 차트 4개를 그린다. 필터를 바꾸면 값이 함께 바뀐다.
  3. 챗봇: 05의 RAG 체인(`retrieve → build_prompt → ask`)을 그대로 옮겨 쓴다. 업종·연도 필터는 ChromaDB `where`로 넘기고, 07에서 만든 `sif_v3`가 있으면 우선 사용한다.
  4. 근거 부족 처리: 유사도 0.40 미만이면 GPT를 호출하지 않고 "제공된 사례에서 근거를 찾을 수 없습니다."를 보여준다. API 오류는 화면에 표시하고 앱은 계속 동작한다.
- **결과**:
  - 대시보드: 분석 사례 6,032건, 2025년 사고사망자 872명, 가장 많은 기인물 지게차(3.6%), 2004→2025 사망자 변화 -32.8%(-426명).
  - 챗봇: 컨베이어 끼임 질문은 사고 원인·예방대책과 출처 사례가 함께 표시된다.
  - 확인한 사실: 업종 필터가 `건설업`인 채로 제조업 질문(지게차 등)을 하면 근거가 없는 것으로 처리된다. 필터가 의도대로 동작한다는 뜻이다. 화면에 "질문 당시 필터"를 함께 표시하게 했다.
- **한계**:
  - 통계 문서의 업종구분은 `통계`라서 업종을 `전체`로 둘 때만 통계 질문에 답한다.
  - 짧은 현장 말투 질문은 검색 유사도가 낮아 근거 없음으로 처리되는 경우가 있다(M6 Hit@5 0.26과 같은 원인).
  - 필터가 걸려 있어도 화면 위쪽에는 눈에 띄는 안내가 없다.
- **파일**: `app/su-lim/08_app.py`, `docs/su-lim/screenshots/m8_*.png`
