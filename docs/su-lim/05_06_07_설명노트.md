## 공통 용어 (먼저 이것만)

| 용어 | 한 줄 설명 |
|---|---|
| 임베딩 | 문장을 숫자 1,536개짜리 벡터로 바꾼 것. 뜻이 비슷한 문장은 벡터도 가깝다. (`text-embedding-3-small`) |
| 코사인 유사도 | 두 벡터가 얼마나 같은 방향인지 (1에 가까울수록 비슷). ChromaDB는 거리(distance)를 주니까 `유사도 = 1 - 거리`. |
| k | 검색해서 가져오는 문서 수. 우리는 답변용 3, 평가용 5. |
| MIN_SIM | 이 유사도보다 낮은 문서는 근거로 쓰지 않는 기준 (0.40). |
| grounded | 답변이 사례에 근거했는지. 근거 없으면 "제공된 사례에서 근거를 찾을 수 없습니다." |
| Hit@K | 정답 문서가 상위 K개 안에 있는 질문의 비율. |
| MRR@5 | 정답이 1위면 1, 2위면 0.5, 3위면 0.33… 5위 밖이면 0 의 평균. 순위까지 반영. |
| 청킹 | 긴 문서를 어떤 단위로 쪼개 넣을지. 우리 사례는 평균 372자라 안 쪼갰고, 통계 표만 쪼갰다(07). |

## 05. RAG 체인 (`05_m5_RAG체인`)

**한 줄 요약** 질문 → 비슷한 사례 3건 검색 → 그 사례만 근거로 GPT가 답변 + 출처 표시. 근거가 없으면 지어내지 않고 거절한다.

### 흐름 (셀 순서)
1. **준비**: `data/chroma`의 `sif` 컬렉션(사례 6,032건)을 연다. `.env`에서 API 키를 읽는다.
2. **`retrieve()`**: 질문을 임베딩 → 가장 가까운 k개 → 유사도가 MIN_SIM 미만이면 버린다. 업종 같은 조건은 `where=`로 걸 수 있다(메타데이터 필터).
3. **`build_prompt()`**: 검색된 사례를 `[사례1] ... [사례2] ...`로 이어 붙이고 마지막에 질문을 붙인다.
4. **`SYSTEM` 프롬프트**: "사례에 있는 내용만 쓸 것", "원인/대책 순서", "근거 없으면 정해진 문장만" 규칙.
5. **`ask()`**: 검색 결과가 없으면 GPT를 부르지 않고 바로 거절(비용·환각 방지). 있으면 `temperature=0`으로 답변 생성. 결과는 `answer / sources / grounded / retrieved`.
6. **5-1 점검**: 범위 안 질문 3개, 범위 밖 질문 3개의 최고 유사도를 비교해서 MIN_SIM을 정한다.

### 우리 결과 숫자와 의미
- 범위 안 질문의 최고 유사도 **최저 0.438**, 범위 밖 질문의 **최고 0.353** → 그 사이인 **0.40**을 기준으로 잡았다. (눈대중이 아니라 두 집단 사이에 선을 그은 것)
- 범위 밖 질문 3개(날씨, 달 탐사선, 파스타)는 전부 "근거 없음". 환각 방지가 동작.
- **알려진 한계**: "지붕 채광판 위에서 작업하다 추락" 질문은 유사도 0.56으로 검색은 됐지만 엉뚱한 사례(거푸집, 작업발판)가 올라와서 LLM이 거절했다. LLM이 틀린 게 아니라 **검색이 틀렸다.** ("작업하다 추락한 사고"라는 흔한 표현에 "채광판"이라는 구체 단어가 묻힘) → M7 후보.

### 예상 질문과 답
- **Q. 왜 k=3인가?** 프롬프트가 길어지면 비용이 늘고 엉뚱한 사례가 섞인다. 사례 1건이 평균 372자라 3건이면 충분하다고 봤다.
- **Q. MIN_SIM을 0.40으로 한 근거는?** 범위 안/밖 질문의 최고 유사도를 직접 재서 사이값으로 정했다(0.438과 0.353).
- **Q. 환각을 어떻게 막았나?** 세 겹이다. ① 유사도 기준 미달이면 GPT를 호출하지 않음 ② 프롬프트로 "사례에 없는 내용 금지" ③ `temperature=0`.
- **Q. 출처는 어떻게 붙나?** 프롬프트에 사례 번호를 붙여 보내고, 답변에 `[사례N]`을 달게 한 뒤, `sources`에 번호별 업종·기인물·연도·개요를 함께 돌려준다.
- **Q. 왜 청킹을 안 했나?** 사례 한 건이 평균 372자로 짧고, 한 건이 한 사고 단위라 쪼개면 맥락이 끊긴다.

### 직접 해볼 것
1. 5-1 표에서 숫자 6개를 눈으로 보고 "왜 0.40인지" 입으로 설명해 보기.
2. `MIN_SIM`을 0.30과 0.50으로 바꿔 날씨 질문과 지게차 질문의 결과가 어떻게 달라지는지 보기.

## 06. 골든 셋 평가 (`06_m6_평가`)

**한 줄 요약** 정답이 있는 질문 100개로 "검색이 정답 사례를 몇 번이나 찾는가"를 숫자로 잰다.

### 흐름
1. **골든 셋 불러오기**: 사례 84(건설 47 + 제조 37) + 통계 16.
2. **정답 근거 검증**: 정답 ID가 실제 DB에 있는지, 정답 확인 문구가 그 문서에 실제로 들어 있는지 확인(사례 82/84 일치. "정답이 명확해야 한다"는 팀 기준).
3. **`evaluate()`**: 질문 임베딩 → 상위 5개 → 정답 순위 계산 → Hit@1/3/5, MRR@5.
4. **못 찾은 문항 보기**, **통계 문항 원인 확인**.
5. **질문 현실성 점검**: 질문이 재해개요 문장을 그대로 베낀 것인지 확인(코덱스 질문 Q06~Q85는 80/84가 사례 본문을 그대로 옮김).
6. **현장 말투 질문으로 재평가**: GPT로 질문을 짧고 현장 말투로 바꿔서 다시 측정.

### 우리 결과 숫자와 의미
| 세트 | Hit@1 | Hit@5 | MRR@5 | 의미 |
|---|---|---|---|---|
| 원본 질문·사례 84 | 0.76 | 0.84 | 0.80 | 좋아 보이지만 질문이 본문을 베낀 것이라 부풀려진 점수 |
| 원본 질문·통계 16 | - | 0.00 | - | 인덱스에 통계 문서가 없어서 검색 자체가 불가 |
| 현장 말투·사례 84 | 0.08 | 0.26 | 0.14 | 실제 사용 환경에 더 가까운 점수 |

- 핵심 해석: **0.84는 실력이 아니라 질문이 쉬워서 나온 점수**이고, 현장 말투로 바꾸면 0.26이다(0.58 하락).
- 단, 현장 말투 질문은 비슷한 사례가 여러 건이라 정답 1건만 인정하면 점수가 낮게 나오는 측면도 있다. 그래서 07에서 "기인물이 같은 사례가 상위 5개에 있는가"도 같이 본다.

### 예상 질문과 답
- **Q. Hit@K와 MRR의 차이?** Hit@K는 "있냐 없냐", MRR은 "몇 번째냐"까지 반영한다.
- **Q. 골든 셋 정답은 믿을 수 있나?** 정답 ID가 DB에 있는지, 정답 문구가 본문에 있는지 코드로 대조했다(82/84). 나머지 2건은 문구를 의역한 경우라 눈으로 확인했다.
- **Q. 왜 질문을 바꿔서 다시 쟀나?** 원본 질문이 사례 문장을 그대로 옮긴 것이라 검색이 너무 쉬웠다. 실제 사용자는 그렇게 묻지 않는다.
- **Q. 통계 0.00은 모델 문제인가?** 아니다. 통계 문서를 DB에 안 넣었기 때문이다(구조적 문제).
- **Q. 평가에 정답 ID가 필요한 이유?** 검색 결과가 정답이었는지 자동으로 채점하려고. 사람이 100개를 일일이 보지 않아도 된다.

### 직접 해볼 것
1. 4-1절 "못 찾은 문항" 표에서 3개를 골라, 1위로 나온 문서가 왜 비슷하다고 판단됐는지 추측해 보기.
2. 6절의 원본 질문과 현장 질문을 5쌍 눈으로 비교하기.

## 07. 개선 실험 (`07_m7_개선실험`)

**한 줄 요약** 06에서 찾은 약점(통계 질문 0.00)을 고치는 실험. 고치기 전과 후를 같은 100문항으로 비교한다.

### 흐름
1. **통계 문서 만들기**: 파일 3(규모별 사고사망자수, 10행×22년)을 문서로 변환. 규모 표기가 파일은 `5-9인`, 질문은 `5인 ~ 9인`이라 두 표기를 같이 적었다.
2. **새 컬렉션 `sif_v2`**: 기존 `sif`를 복사(임베딩 재사용) + 통계 문서 10건. 기존 것을 건드리지 않는 이유는 비교 기준(개선 전)을 보존하려고.
3. **같은 평가 함수·같은 질문 임베딩**으로 개선 전/후 측정.
4. **부작용 점검**: 사례 성능이 떨어졌는지, 사례 질문 상위 5개에 통계 문서가 섞였는지.
5. **통계 답변 정확도**: 검색뿐 아니라 LLM이 숫자를 맞게 읽는지.
6. **MIN_SIM 통과 여부**: 검색돼도 유사도 0.40 미만이면 챗봇은 답하지 못한다.
7. **진단 → 2차 개선(`sif_v3`)**: 문서를 규모×연도 단위(220건)로 쪼갬.

### 우리 결과 숫자와 의미 (1차, v2)
- 통계 Hit@5 **0.00 → 0.56**, 통계 답변 정확도 **0.00 → 0.38**. (컬렉션을 다시 만들 때마다 흔들려서 Hit@5는 0.56~0.69, 답변 정확도는 0.3~0.4 범위였다.)
- 사례 Hit@5 0.84 → 0.86은 **개선이 아니라 오차**다. 컬렉션을 새로 만들면 검색 인덱스(HNSW, 근사 검색)가 다시 짜지면서 한두 문항이 달라질 수 있다.
- **0.56은 우연에 가깝다.** 통계 문서가 10건이라 무작위로 5개를 골라도 Hit@5가 0.50이다. 정답 문서의 유사도가 전부 0.60~0.65에 몰려 있어 규모를 구분하지 못했다(원인: 한 문서에 22개 연도 숫자가 다 들어가 문서끼리 비슷해짐).
- 그래서 문서를 "숫자 하나 = 문서 하나"로 쪼갠 v3를 만들었다. (v3 결과: 통계 Hit@5 **1.00**, 통계 답변 정확도 **1.00**, 사례 Hit@5 0.86(정확 검색 기준 0.869로 개선 전과 동일), MIN_SIM 통과 16/16(정답 문서 유사도 최소 0.749). 단 v3는 규모+연도까지 맞아야 정답이라 v2보다 엄격한 기준이다.)

### 예상 질문과 답
- **Q. 왜 이 개선을 골랐나?** 06에서 가장 큰 구멍(통계 16문항 전부 0)이었고, 원인이 명확해서(인덱스에 문서가 없음) 효과를 깔끔하게 검증할 수 있다.
- **Q. 왜 새 컬렉션을 따로 만들었나?** 개선 전 상태를 보존해야 같은 조건에서 비교할 수 있다. 임베딩은 복사해서 비용도 거의 안 들었다.
- **Q. 사례 +0.02는 개선인가?** 아니다. 인덱스를 새로 만들 때 생기는 근사 오차 범위(±0.03)로 해석한다.
- **Q. 1차에서 왜 멈추지 않고 2차를 했나?** 0.56이 무작위 기준(0.50)과 비슷했고, 정답 유사도가 규모별로 거의 차이가 없다는 걸 진단으로 확인했기 때문이다.
- **Q. v3의 평가가 왜 더 엄격한가?** 정답을 규모+연도까지 맞아야 인정한다(예: `통계-5-9인-2025`).
- **Q. 이 방법의 한계는?** 통계가 규모별 사망자수 한 가지뿐이다. 업종별·재해유형별 통계 질문은 답하지 못하고, 현장 말투 사례 검색(0.26)은 그대로다.

### 직접 해볼 것
1. 8-1 비교표에서 세 열(개선 전/v2/v3)을 읽고 "무엇이 좋아졌고 무엇이 그대로인가"를 두 줄로 쓰기.
2. 7절의 "유사도 차이 평균"이 왜 중요한지(작을수록 구분이 안 된다는 뜻) 설명해 보기.

## 한 장 요약 (노션·발표용)

- **M5**: 질문→사례 3건 검색→사례만 근거로 답변+출처. 유사도 0.40 미만이면 거절(범위 안 최저 0.438 / 범위 밖 최고 0.353에서 도출).
- **M6**: 골든 100문항 평가. 원본 질문 Hit@5 0.84이지만 질문이 본문을 베낀 탓이고, 현장 말투로 바꾸면 0.26. 통계는 문서가 없어 0.00.
- **M7**: 통계 문서를 추가한 `sif_v2`로 통계 Hit@5 0.00→0.56. 단 무작위 기준 0.50과 비슷해서 진단 후 규모×연도 단위로 쪼갠 `sif_v3`로 2차 개선(통계 Hit@5 1.00, 답변 정확도 1.00, 사례 성능 유지).
