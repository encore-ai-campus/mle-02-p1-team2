## 기본·중급 RAG 범위

| 수준 | 이번 프로젝트에서의 위치 | 사용자 흐름·기술 | 시작 조건 |
| --- | --- | --- | --- |
| 기본: 검색되는 RAG | **먼저 완성할 MVP** | 작업·위험 상황 질문 → 유사 SIF 사례/공식 문서 상위 3건 → 원인·예방대책 요약 → 원문 출처 표시. Pandas 정제, LangChain, 임베딩, ChromaDB, LLM, Streamlit | 출처가 검증된 코퍼스와 `doc_id` 확보 |
| 중급: 맥락형 안전 RAG | **10/7 목표 범위** | 업종·작업·장비 맥락 유지, 짧은 대화 이력, 메타데이터 필터, 사고사례와 공식 안전기준 근거 구분, 근거를 붙인 TBM 체크리스트 초안 | 기본 RAG 점수·오답 원인 확인, 안전기준 원문·이용조건 확보 |

새 그림의 하급 흐름에는 PostgreSQL이, 노션 기술 스택과 현재 프로젝트에는 ChromaDB가 적혀 있다. **제출용 MVP는 이미 준비된 ChromaDB로 구현**하고, PostgreSQL/pgvector 사용은 팀이 저장·운영 요구를 확정한 뒤 별도 결정한다. 저장소를 바꾸는 일이 검색 품질 평가와 앱 완주를 밀어내지 않게 한다. 그림의 CSI·KOSHA 사고사례·KOSHA GUIDE·안전규칙은 실제 문서와 이용조건을 확보한 뒤 중급 코퍼스 후보로 검증한다.

중급의 TBM 체크리스트는 **검색 근거에 적힌 조치만 제시**하고, 현장별 위험성평가·전문가 판단을 대체하는 확정 지시로 표현하지 않는다. 근거가 없거나 통계 기간이 다르면 답변에 그 한계를 표시한다.

## 데이터·코드 연결 규칙

1. 각 원본은 `source_XX`와 수집 일시·출처 URL·SHA-256으로 추적한다. 원본 덮어쓰기 없이 재실행할 수 있는 수집·전처리 코드를 남긴다.
2. 정제 파일은 자료별로 저장한다. ②~⑤ 결합 결과는 `dashboard_metrics.parquet`, ①은 검증한 `source_01_sif_cases.parquet`를 사용한다. ②~⑤의 실제 열을 확인한 뒤 스키마를 확정한다.
3. RAG 코퍼스에는 `doc_id`, `source_id`, 원본 URL, 제목, 기관, 기준일, 내용 범위를 기록한다. 답변 화면에는 문서 제목·원본 링크를 보여준다.
4. 평가에서는 동일한 질문·코퍼스·임베딩·top-k를 유지하고 개선 요소만 바꾼다. 실패 원인과 재현 방법을 보고서에 남긴다.
5. `notebooks/personal/`과 `data/personal/`은 개인 작업 공간이다. 팀 공용 `src/`, `app.py`, `data/`에 확정본을 옮길 때 이용조건·변경 이유·검증 결과를 기록하고 PR 리뷰를 받는다. `.env`와 원본 대용량 파일은 Git에 올리지 않는다.
