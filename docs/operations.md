# 프로젝트 작업 운영 가이드

여러 프로젝트에서 목표와 완료 기준을 일관되게 관리하고, AI 초안 작성과 사용자 검토를 효율적으로 연결하기 위한 기본 양식입니다.

## 운영 원칙

1. **목표와 완료 기준부터 정합니다.** 기능 목록보다 최종 산출물과 완료를 확인할 방법을 먼저 적습니다.
2. **한 번에 한 작업 단위를 끝냅니다.** 새 기능으로 넘어가기 전에 현재 단계의 실행 결과와 남은 문제가 무엇인지 확인합니다.
3. **기존 작업을 확인하고 재사용합니다.** 코드, 데이터, 문서, 환경 설정을 살핀 뒤 변경 범위를 작게 잡습니다.
4. **작은 선택은 자율적으로 처리합니다.** 되돌릴 수 있는 구현 선택은 AI가 판단해 진행하고 이유를 결과 보고에 남깁니다.
5. **영향이 큰 행동은 미리 확인합니다.** 외부 공개·배포, 대량 또는 유료 API 사용, 파괴적 데이터 변경처럼 되돌리기 어렵거나 비용이 큰 일은 실행 전에 범위와 영향을 알립니다.
6. **검토 가능한 결과물을 먼저 만듭니다.** 계획만 반복하지 않고, 실행 가능한 초안을 만든 뒤 필요한 검증을 거쳐 사용자에게 제시합니다.
7. **상태는 근거와 함께 보고합니다.** `PASS`는 실제 실행·검증한 항목, `HOLD`는 아직 확인되지 않은 항목, `REJECT`는 실패해 채택하지 않은 항목에 사용합니다.
8. **진행률은 단계 기준으로 계산합니다.** 근거가 없는 정밀 백분율은 피하고, 미완료 완료 기준을 함께 제시합니다.
9. **팀 리뷰는 요청 시 준비합니다.** 사용자가 요청하지 않은 팀 연락, 리뷰 요청, 외부 공유는 하지 않습니다.

## 프로젝트 시작 브리프

새 프로젝트마다 아래 내용을 한 번 작성합니다. 아직 모르는 항목은 비워 두고, AI가 저장소나 제공 파일을 확인해 초안을 제안하도록 합니다.

```text
프로젝트명:
목표:
최종 산출물:
완료 기준(어떻게 확인할지):
이번 단계에서 할 일:
이번 단계에서 제외할 일:
데이터·비용·환경·일정 제약:
사용자가 직접 검토하거나 승인할 지점:
```

## 단계별 작업 흐름

### 1. 착수

- 저장소의 기존 설계·코드·데이터·작업 상태를 확인합니다.
- 목표, 완료 기준, 주요 제약을 요약합니다.
- 중요한 선택지가 미정이면 먼저 영향과 기본안을 제시합니다.

### 2. 구현

- 완료 기준 하나를 선택해 작은 변경으로 구현합니다.
- 기존 기능과 사용자의 변경사항을 보존합니다.
- 비용·외부 효과가 있는 작업은 실행량과 영향을 먼저 점검합니다.
- API나 DB 작업은 작은 표본으로 연결을 확인한 뒤 전체 처리로 넓힙니다.

### 3. 자체 확인

- 변경한 코드의 구문, 실행 흐름, 입력·출력, 오류 경로를 점검합니다.
- 결과물의 출처·식별자·데이터 범위가 유지되는지 확인합니다.
- 확인하지 못한 조건은 통과했다고 표현하지 않습니다.

### 4. 사용자 검토

AI는 변경 파일, 실행 결과, 남은 문제를 한 번에 요약합니다. 사용자는 아래처럼 간단히 피드백할 수 있습니다.

```text
유지:
수정:
다음 우선순위:
```

### 5. 완료 또는 다음 단계

- 피드백을 반영한 뒤 해당 완료 기준을 다시 확인합니다.
- 단계가 끝나면 다음 의존 작업을 제안하고, 짧은 지시(예: “다음”)가 오면 그 작업부터 이어갑니다.
- 외부 공개·배포·파괴적 변경은 구체적인 최종 결과를 준비한 후 필요한 확인을 받습니다.

## 기본 완료 보고 양식

```text
상태: PASS / HOLD / REJECT

완료:
- 변경 내용과 이유

확인:
- 실행한 명령 또는 확인 방법과 실제 결과

산출물:
- 파일 경로

남은 항목:
- 미완료 기준이나 막힌 조건

다음 우선순위:
- 가장 효율적인 후속 작업 한 가지
```

## 검토·승인 경계

| 작업 | 기본 진행 방식 |
|---|---|
| 읽기, 분석, 로컬 초안 및 되돌릴 수 있는 코드 수정 | 범위가 명확하면 진행 후 보고 |
| 작은 표본 API 호출, 로컬 실행 | 요청 목적과 기존 승인 범위 안에서 실행량을 제한 |
| 대량·유료 API 호출 또는 비용 증가 | 처리량과 예상 영향을 먼저 알리고 확인 |
| 외부 서비스에 메시지 전송, 게시, 공개 배포 | 구체적인 결과물을 준비한 뒤 사용자 승인 |
| 원본·라벨·비밀 설정 덮어쓰기, 파괴적 작업 | 진행하지 않고 먼저 확인 |

## 권장 문서 구성

프로젝트마다 문서를 늘리지 말고 아래 정도로 유지합니다.

- `PROJECT_BRIEF.md`: 목표·완료 기준·범위·제약을 기록하는 한 페이지 브리프
- `README.md`: 실행 방법과 현재 기능 안내
- `DECISIONS.md`: 여러 작업에 영향을 주는 설계 선택과 이유가 누적될 때만 사용
- `TASKS.md` 또는 이슈 보드: 남은 일의 단일 목록. 같은 작업을 여러 곳에서 중복 관리하지 않음
